# 排期与预约卡片架构约定

> 本文是 `ARCHITECTURE-UPGRADE.md` 的排期管理专项补充。后续优化必须继续遵守“后端事实源、前端只呈现、关键变化可追溯”的总体原则。

## 1. 数据职责

- `appointments` 是预约事实与历史凭证，保存预约时间、技师、客户、服务项目、预约时的服务序号和总次数快照。
- `orders` 是套餐服务总次数的实时事实源。预约通过 `appointments.order_id` 绑定创建时选中的具体订单。
- 页面展示总次数时优先读取关联订单的 `orders.total_times`；仅历史预约无法匹配订单时，才回退到 `appointments.service_total_times` 快照。
- 确认已服务时必须按 `order_id` 更新对应订单，禁止只按客户取最新订单，以免多阶段订单串单。
- 已取消预约只在预约列表保留历史，不占用排期时段，也不在排期日历显示。

## 2. 卡片统一读模型

排期卡片固定依次展示：技师（仅总览）、客户、客服、区域、时间、项目、业务补充信息、备注、服务状态。业务类型只通过卡片颜色区分，不再单独占用一行：橙色为体验卡、蓝色为套餐。套餐的业务补充信息展示“已服务/总次数”，体验卡在同一位置展示关联订单的“已付款/未付款”；两类卡片使用相同的紧凑固定高度。备注无内容时仍保留“备注：”标签。单行溢出使用省略号，完整内容通过悬停提示和点击详情查看。

点击卡片只打开当前页面的只读预约详情，不改变预约状态。筛选菜单固定在页面滚动视口顶部，日期表头固定在排期滚动区域顶部；两层置顶区域必须使用不透明背景、独立层叠上下文和明确层级，禁止日历内容在滚动时穿透。

### 手机端周历

- 手机端排期表采用“固定时段列 + 单日满宽列 + 整周横向滑动”：时段列 52px、日期列宽度为 `calc(100vw - 76px)`，每次完整展示一天并强制吸附，预约卡片高度 224px。
- 手机端卡片基本字段允许换行完整展示；桌面端保持紧凑省略显示，鼠标经过仍可查看完整信息。

## 3. 服务确认边界

- 只有预约日期小于或等于本地业务日期、且未取消、未完成的预约显示“确认服务”。
- 已完成预约在相同位置固定显示“已完成服务”。
- 未来预约不得提前确认，并在相同位置显示“已预约未做”。
- 确认接口负责创建服务凭证并幂等更新订单已服务次数，不能由前端直接计算后写回。

## 4. 数据迁移与兼容

- 迁移 `027_appointment_order_link` 新增并索引 `appointments.order_id`。
- 历史数据按客户、订单阶段和最接近的服务总次数进行一次性回填。
- 无法可靠回填的数据允许保留为空，读取时使用快照兜底，避免错误绑定。

## 5. 回归基线

每次调整排期功能至少验证：取消预约不展示、三城市区域筛选、卡片结构与详情弹窗、固定筛选菜单与表头、未来显示“已预约未做”、当天及历史显示“确认服务”、完成后显示“已完成服务”、实时订单总次数、确认服务幂等及排期冲突校验。

## 6. 订单次数同步与服务冲销

- 迁移 `028_appointment_progress_audit` 建立三类不可替代的业务凭证：完成服务对订单次数的实际影响、订单次数同步基线、错误完成服务冲销。业务写入只能通过预约领域服务执行。
- “同步订单次数”以关联订单当时的 `used_times/total_times` 为排期基线，保存订单、客户、业务类型、同步前后值、操作人和时间。同步后的新预约继续由后端按“已服务次数 + 1”生成服务序号。
- 完成服务时在同一事务内写入 `appointment_progress_events`，记录订单次数和服务人员分配的变更前后值；唯一预约索引与 `progress_applied_at` 共同保证网络重试、重复点击和并发确认不会重复累计。
- 已完成服务禁止直接取消或删除。冲销必须填写原因，并在同一事务内锁定预约、完成事件和订单，回退本次事件造成的次数增量，将预约标为“已冲销”，同时冻结服务记录和工资结算凭证。原服务记录不删除。
- `appointment_service_reversals` 保存原服务快照、受影响数据、原因、操作人、角色和时间；预约唯一索引拒绝重复冲销。已冲销预约与已取消预约相同，不占用档期，但继续保留在历史列表中。
- 同步与冲销接口仅允许 `superadmin`、`admin`、`service` 角色，权限必须由后端中间件校验。

### 迁移与回滚

部署前备份 RDS。迁移只新增表和可空列，不修改历史业务值。应用回滚时可先回滚代码并保留新增审计表；如必须回退结构，应在确认不存在 `appointment_service_reversals`、`appointment_progress_syncs` 和 `appointment_progress_events` 新数据后，再删除迁移 028 新增的表、列及对应的 `schema_migrations` 记录，禁止在已有冲销凭证时直接删表。
